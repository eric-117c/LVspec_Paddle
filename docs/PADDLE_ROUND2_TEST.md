# 第二轮优化：五视频解码加速超过 2.2×

验证日期：2026-11-01。本轮完整测试的解码吞吐比为 **2.212162552×**，
两遍分别为 **2.210730482×、2.213596144×**，均超过 2.2×。
含 prefill 吞吐比为 **1.674198428×**。这仍是五个固定视频的结论，不是全数据集保证。

## 本轮改动

| 文件 | 改动 | 正确性与代价 |
| --- | --- | --- |
| `paddle_backend/draft_graph.py` | 将根 token 和前缀位置放入一个持久输入 buffer，直接从 NumPy 更新 | 减少两个临时 CUDA tensor 的创建和分开的拷贝；回放时共享视图需保持有效 |
| 同上 | 一次生成草稿块中全部位置、RoPE gather 和 additive mask，再按步使用 | 保持各 token 的位置/可见性，减少重复小算子调用 |
| `paddle_backend/decoding.py` | 一次读取接受长度、候选及后续根预测 | 将原来的多次主机读取合并；EOS 与生成上限规则不变 |
| 同上 | 缓存请求内不变参考隐藏状态的 FP32 归一化分块 | 首次构造在解码计时内，之后复用；额外保存参考块，随请求释放 |
| `tests/paddle/test_backend.py` | 验证不同候选形状下缓存/不缓存参考块的结果相同 | 结合现有单链与通用路径、Graph 回滚及完整接受检查 |

本轮没有改变剪枝率、宽松接受参数、候选链或生成上限，也没有修改 AR 的模型计算路径。
正常 eager 分支仍可用。所有准备、首次参考块归一化和每请求 Graph 捕获均包含在原有计时范围内。

## 完整测试设置

- 目标 Qwen2.5-VL-32B 在物理 GPU 1，草稿 7B 在 GPU 3；两张 A100 80GB。
- Paddle GPU 3.3.1、FP16、greedy、batch size 1、SDPA、Graph 与投影打包开启。
- 与 2026-10-20 测试相同的五份 NPZ，输入 SHA256 全部一致；每视频 64 帧，上限 512 token。
- 每方法预热后交替运行，每视频各重复两次，共 20 次生成。
- 使用常驻模型执行原 `tools/benchmark_paddle.py` 测量循环；模型只加载、打包一次，
  加载/打包本来就在计时外。运行封装、命令、变体及源码哈希均保存以供核查。
- 119 次约每 5 秒的采样未观察到同卡其他计算进程；采样不能排除间隔中的短任务和主机共享影响。

## 性能结果

| 指标 | AR | LVSpec | 比值 |
| --- | ---: | ---: | ---: |
| 解码吞吐，token/s | 13.5804 | 30.0420 | **2.2122×** |
| 含 prefill 吞吐，token/s | 12.2638 | 20.5320 | **1.6742×** |
| 平均推理时间，秒 | 41.7490 | 19.1506 | 耗时比 2.1800× |
| 平均生成 token 数 | 512.0 | 393.2 | 回答长度不同 |

吞吐按总 token/总时间计算；推理时间排除模型加载和视频预处理。
2.1800× 耗时比包含回答长度变化，不能替代吞吐比。

| 视频 | AR token/s | LVSpec token/s | 解码加速比 |
| --- | ---: | ---: | ---: |
| 电视节目 | 16.4181 | 34.1396 | 2.0794× |
| 风帆冲浪 | 13.2420 | 26.9798 | 2.0374× |
| 理发 | 12.8378 | 27.9678 | 2.1785× |
| 越野摩托车 | 12.8346 | 29.9056 | 2.3301× |
| 木桌清洁 | 13.1675 | 31.4221 | 2.3863× |

第一遍 AR/LVSpec 为 13.5819/30.0260 token/s，第二遍为 13.5788/30.0579 token/s。
不是每个视频都达到 2.2×；目标按五视频的总量吞吐比判断。

## 同权重旧版对照

完整新版本测试之后，在同一批已加载权重、同样设备上加载上一提交的解码/Graph 源码快照，
对原输入索引 2（理发，8107 prompt token）再跑两遍 AR/LVSpec，共四次生成，均为 512 token。

| 版本 | AR token/s | LVSpec token/s | LVSpec / AR |
| --- | ---: | ---: | ---: |
| 旧版快照 | 12.8244 | 27.8866 | 2.1745× |
| 新版，同用例完整测试记录 | 12.8378 | 27.9678 | 2.1785× |

该用例 LVSpec 绝对吞吐提高约 **0.29%**，输出及平均接受长度完全相同。
对照的 30 次 GPU 采样未观察到其他计算进程。
这组对照只有一个输入，顺序是新版在前、旧版在后，未随机交叉，不能据此声称提升具有统计显著性。
也不能将此前 2.1948× 与本轮 2.2122× 的跨日期整批差异全部归于代码变化。
本轮确认的是两遍完整实测均超过 2.2×，余量仍小，后续运行可能波动。

## 正确性与质量

CPU 后端/CLI/指标检查 **26 passed**，GPU 检查 **9 passed**，合计 **35 passed**。
参考块缓存与非缓存计算逐元素相同；现有检查还覆盖了严格/宽松/PST 的单链对照、
FP16/BF16 Graph 输入变化、KV 回滚和完整接受。

本轮 20 条结果的 token IDs 与上一轮五视频完整测试全部一致，同方法两次重复也完全一致。
因此沿用相同问题/参考/预测哈希的已保存裁判结果，没有再次执行裁判模型推理。
正确性/覆盖度仍为 AR **3.6/5**、LVSpec **3.4/5**，ROUGE-L F1 分别为 0.1604、0.1926。
这说明本次调度优化没有改变已测用例的输出，不表示 LVSpec 相对 AR 无损，
也不取代真实大模型严格数值对齐或独立质量评估。
